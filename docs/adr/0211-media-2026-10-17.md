# ADR 0211 media addendum — 2026-10-17

Outbound media decisions for the WeChat bridge (issue #132). This note is a
dated addendum to [ADR 0211](0211-wechat-ilink-channel.md) §10, which states
that Agent-produced media is uploaded through Tencent's encrypted CDN but does
not define which content is eligible.

## Eligible source

The only eligible source is a structured ACP `resource_link` content block
with a `file://` URI inside an Agent message chunk of a run. Model text is
never parsed for paths or Markdown image links, inline `image` content blocks
are not delivered in the first release, and links outside a run have no
recipient and are not recorded.

The journal records an `agent_media_refs` row (opaque id, conversation, run,
URI, provider-declared size, bounded caption) and then publishes a
`media_shared` run event whose payload is only `{media_id, kind, mime}`. The
URI, file name, and caption never appear in workspace events, browser
payloads, analytics, or logs. Rows cascade with their conversation and are
bounded per conversation.

## Resolution and limits

The outbound bridge resolves a `media_shared` event by opaque id, scoped to
the conversation that shared it, through `WorkspaceService`:

- the path must lie inside the Session execution root (Project root or the
  Session's own worktree) and reach a regular file through plain directories —
  no symlink, hidden, `.`, or `..` component;
- the extension must be on the allowlist (PNG, JPEG, GIF, WebP, and BMP as
  images; PDF, plain text, Markdown, CSV, JSON, ZIP, DOCX, XLSX, and PPTX as
  files) and the content must match it by signature — executables are refused
  regardless of name;
- the file must not exceed 10 MiB, must match a provider-declared size when one
  exists, and must be the same inode and size before, during, and after the
  bounded read.

Video and audio remain unsupported. Rejections produce one localized notice
to the originating peer and never reveal the file name or path.

## Wire behavior

Each delivery follows the reviewed upstream send path: random file key and
AES-128 key, plaintext MD5, PKCS#7 ciphertext size, `getuploadurl` with
`no_need_thumb`, a bounded-retry CDN upload to a validated origin, then one
`sendmessage` per item. An optional caption is its own text message before
the media. `CDNMedia.aes_key` is base64 of the 32-character hex key string
(upstream `Buffer.from(aeskeyHex).toString("base64")`) with `encrypt_type`
1; image items carry the ciphertext size as `mid_size`, file items carry
`file_name` and the plaintext size as `len`. The earlier implementation
encoded the raw key bytes, which did not match upstream; this addendum
corrects it.

Media buffers exist only in memory for the duration of one delivery and are
dropped on success, failure, cancellation, and shutdown; nothing is written to
disk.
