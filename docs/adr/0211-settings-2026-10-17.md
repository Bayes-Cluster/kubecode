# ADR 0211 settings addendum — 2026-10-17

Browser connection-settings decisions for the WeChat bridge (issue #134). This
note is a dated addendum to [ADR 0211](0211-wechat-ilink-channel.md) §5, which
specifies that the QR login route returns an SVG data URI.

## Server-rendered QR images

Upstream `get_bot_qrcode` returns `qrcode_img_content`, a scan-target URL that
must be encoded into a QR image (the reviewed plugin renders it with
`qrcode-terminal`). Kubecode renders it on the server with the `qrcode` crate
(MIT/Apache-2.0, SVG renderer only, no default features, no transitive
dependencies) and returns only a `data:image/svg+xml;base64,…` image as
`qr_svg`. The browser never receives the scan target as text, so it cannot be
stored, copied, logged, or sent to telemetry; the upstream QR identifier used
for status polling never leaves the service. Scan targets longer than 1 KiB are
refused.

## Login generations

Every newly issued QR — a fresh start or an automatic refresh — increments a
login generation exposed as `login_generation` in status payloads and as
`generation` when a login starts. `POST /ilink/login/verify` accepts the
generation the code was typed against and rejects a mismatch, so a code typed
for an earlier QR is never applied to the current attempt. A reused QR keeps
its generation.

## Browser behavior

The Settings section keeps only a safe projection of status (categorical state,
display name, a linked flag, generation, and expiry). It loads status when it
opens, refetches on `ilink_status_changed` workspace events, and polls only
`/ilink/login/qr/poll` while a login is in progress, because QR sub-states are
not published as workspace events. Responses are fenced so an older reply never
overwrites a newer state. Telemetry carries only the action name and a
categorical result.
